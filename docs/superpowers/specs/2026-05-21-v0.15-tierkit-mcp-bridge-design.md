# v0.15 — Tierkit MCP Bridge

**Status:** design draft · 2026-05-21
**Scope:** v0.15.0 ships a Model Context Protocol server that exposes Tierkit's gated tools to any MCP-aware client (Claude Code, Claude Desktop, Claude CLI). Tierkit becomes the local policy-gated tool gateway; the LLM-side agent remains in the calling client.

---

## 1. Why this exists

After the v0.14.2 release, the Claude Agent SDK spike ([`2026-05-21-claude-agent-sdk-spike.md`](../spikes/2026-05-21-claude-agent-sdk-spike.md)) confirmed:

- **Path A is not viable.** `@anthropic-ai/claude-agent-sdk` is a Claude-CLI-backed agent runner, not a pure model client. Tierkit cannot insert itself between the SDK and Anthropic.
- **Path B is feasible but weakens redaction.** Wrapping the SDK with `canUseTool` hooks preserves approval, command-gate, and usage logging, but conversation history and tool-loop context are managed inside the Claude CLI subprocess. Tierkit can pre-redact the initial prompt but cannot enforce redaction across an accumulating session.

Stakeholder decision: **HOLD Agent SDK integration**. v0.15 pivots to the alternative the spike's stakeholder identified — **MCP Bridge**. Tierkit publishes its safe tools as an MCP server. Claude Code remains the agent, with its own conversation orchestration. Tierkit's job is what it has always been best at: workspace boundary enforcement, secret redaction, approval gating, command classification, diff preview, and activity logging — applied at the tool boundary, not the prompt boundary.

This re-positioning sharpens the product:

> Tierkit is **not** a replacement for Claude Code. Tierkit is the **local policy-gated tool gateway** that Claude Code (and Roo, Cline, Continue, or any MCP-aware agent) calls into for file and command operations.

## 2. Non-goals

- Do **not** ship Claude Agent SDK as a normal `ProviderClient` in v0.15. The `claudeCode` profile from v0.14.2 stays as-is (single-shot planner for OpenAI-compat and Tierkit Chat).
- Do **not** own Claude Code's conversation history. The MCP server is stateless with respect to dialogue.
- Do **not** claim Tierkit redacts prompts the user types directly into Claude Code. Tierkit's redaction applies to tool-call inputs and tool-call outputs that pass through Tierkit, not to the prompt-text channel that the client owns.
- Do **not** expose raw `write_file`, `bash`, or direct mutation tools in v0.15. All file modifications flow through `propose_patch` → `apply_patch`. All command execution flows through `run_command` with the existing command-gate classifier.

## 3. Architecture

```
Claude Code / Claude Desktop / Claude CLI
   │  (configured via ~/.claude/settings.json mcpServers: tierkit)
   ▼
   spawn: `tierkit mcp serve --workspace <cwd>`
   │  stdio transport — JSON-RPC over stdin/stdout (MCP standard)
   ▼
@tierkit/mcp-server  (new package, talks to @tierkit/core)
   │
   ▼
For each tool call:
  1. Workspace boundary check       (reject paths outside --workspace)
  2. Ignore-globs check             (.tierkit/ignore, .gitignore-respect)
  3. Tool-specific policy gate
       ├─ read_file / list_files / codebase_search → secret redaction on output
       ├─ propose_patch              → risk scoring + persist ticket
       ├─ apply_patch                → freshness check + approval gate + apply
       └─ run_command                → command-gate classifier + approval gate
  4. Activity log entry → .tierkit/runtime/usage.jsonl
   │
   ▼
Reuse existing @tierkit/agent tools as the actual implementations:
  - listFiles.ts, readFile.ts, codebaseSearch.ts, searchAndReplace.ts,
    applyDiff.ts, executeCommand.ts, safePath.ts
```

**Transport.** MCP standard local transport is stdio over subprocess. The MCP client (Claude Code) spawns the server with the configured command/args, then exchanges JSON-RPC messages over the pipes. No HTTP server, no network sockets. The MCP server lifetime equals the calling client's session.

**Process model.** One Tierkit MCP server per workspace per MCP-client session. Concurrent invocations of the same tool inside a session are serialized at the tool-call boundary (Claude Code already does this); we don't need internal queueing.

**Reuse, not rewrite.** The actual tool implementations already exist in `@tierkit/agent` (Tierkit's own agent tools). The MCP server is a thin protocol adapter that translates MCP `tools/call` messages into the existing tool-handler signatures and packages results back as MCP `content` blocks.

## 5. CLI command

```
tierkit mcp serve --workspace <path>
```

- `--workspace <path>` (required): absolute path to the workspace root. All file operations are sandboxed within this directory.
- `--config <path>` (optional): override the Tierkit config file location (default: `<workspace>/tierkit.config.json`).
- `--log-level <level>` (optional): `error|warn|info|debug` (default: `warn`). MCP requires stdout to be clean JSON-RPC, so logs go to stderr.

The command runs in the foreground, reading MCP requests from stdin and writing responses to stdout, until the parent process closes the pipes. No daemon coordination — each MCP client session spawns its own server.

## 6. MCP tool surface (v0.15.0)

Seven tools. Each is a thin wrapper that:
1. Validates inputs against the workspace boundary
2. Calls into the underlying `@tierkit/agent` tool (or new MCP-specific logic for patches)
3. Applies redaction to any output that could contain secrets
4. Writes an activity log entry
5. Returns an MCP `content` block

| Tool | Mutates? | Approval? | Notes |
|---|---|---|---|
| `tierkit.list_files` | no | no | wraps existing listFiles; respects .gitignore + .tierkit-ignore |
| `tierkit.read_file` | no | no | output redacted via existing engine |
| `tierkit.codebase_search` | no | no | output snippets redacted |
| `tierkit.propose_patch` | no (creates ticket) | no (ticket creation is gated by workspace+ignore checks only) | risk-scored, returns `patchId` + diff preview |
| `tierkit.apply_patch` | **yes** | **yes** when risk ≥ medium OR profile/policy demands it | accepts ONLY `patchId`; not raw diff |
| `tierkit.run_command` | side-effects | **yes** for any command outside the safe-classify list | wraps existing command-gate classifier |
| `tierkit.get_policy_status` | no | no | returns current workspace policy snapshot (ignore globs, approval mode, redaction rules, recent gate denials) |

Tools NOT in v0.15.0 (deferred or refused):
- `write_file` (raw) — refused permanently for v0.15.x
- `apply_patch({ diff })` (raw diff input) — refused; `apply_patch` only takes `patchId`
- `delete_file` — defer to v0.15.1 if usage demand exists
- `git_*` tools — defer; the calling agent can use Claude Code's built-in git tools, which run outside Tierkit's gate
- `move_file`, `create_directory` — defer

## 7. Patch ticket state model

`tierkit.propose_patch` and `tierkit.apply_patch` cooperate through an **ephemeral patch ticket** stored on disk. This is the single most load-bearing safety decision in v0.15.

### propose_patch

```
propose_patch({ files: [{ path, newContent? | diff? }], note? })
  → validate paths are inside workspace
  → check ignore globs (refuse .tierkit/, .env, secrets, etc.)
  → normalize all changes into a unified diff
  → score risk (medium = source file changes; high = config/build/secrets-adjacent)
  → compute beforeHash for each target file
  → write proposal to .tierkit/runtime/mcp/patches/<patchId>.json
  → return { patchId, diff, files, risk, requiresApproval }
  → DO NOT mutate any file
```

Proposal file shape:

```json
{
  "patchId": "patch_01HY...",
  "createdAt": "2026-05-21T...",
  "workspaceRoot": "/Users/.../project",
  "source": "mcp",
  "proposedBy": "claude-code",
  "files": [
    {
      "path": "src/foo.ts",
      "beforeHash": "sha256:...",
      "afterHash": "sha256:..."
    }
  ],
  "diff": "...",
  "risk": { "level": "medium", "reasons": ["modifies source file"] },
  "requiresApproval": true,
  "status": "proposed"
}
```

### apply_patch

```
apply_patch({ patchId })
  → load .tierkit/runtime/mcp/patches/<patchId>.json
  → if status !== "proposed" → refuse with code: invalid-status
  → if createdAt older than 24h → refuse with code: expired-patch
                                  + transition status to "expired"
  → for each file: compute current hash, compare to beforeHash
    → mismatch → refuse with code: stale-patch
                + DO NOT auto-transition status (allow re-propose)
  → if requiresApproval:
    → check approval policy (workspace setting; default: prompt via GUI)
    → if not approved → return { pending: true, approvalUrl: "/v1/mcp/patches/<id>" }
    → approval is asynchronous: Claude Code's caller polls or waits
  → apply the diff (atomic per file: write tmp + rename)
  → transition status to "applied"
  → write activity log entry with patchId, files, risk
  → return { applied: true, files, durationMs }
```

`apply_patch` does **not** accept a raw `diff` argument. The only way to apply a change is to first call `propose_patch` and receive a `patchId`. This makes the propose→review→apply sequence non-skippable, which preserves Tierkit's policy gate guarantees.

### TTL and cleanup

- Tickets older than 24h are treated as expired on read.
- A small `tierkit mcp serve` startup task sweeps `.tierkit/runtime/mcp/patches/` and deletes files with `status: "applied"` or `status: "rejected"` older than 7 days, and `status: "expired"` older than 24h.

### Error codes

```
{ ok: false, code: "outside-workspace",   message: "..." }
{ ok: false, code: "ignored-path",        message: "..." }
{ ok: false, code: "stale-patch",         message: "Target file changed after this patch was proposed. Re-run propose_patch." }
{ ok: false, code: "expired-patch",       message: "..." }
{ ok: false, code: "invalid-status",      message: "..." }
{ ok: false, code: "approval-required",   message: "Patch requires approval. See <approvalUrl>." }
{ ok: false, code: "approval-rejected",   message: "..." }
{ ok: false, code: "command-blocked",     message: "..." }
{ ok: false, code: "redaction-failed",    message: "..." }
```

## 8. Policy gates

Each gate is a small named function inside `packages/mcp-server/src/` (or imported from `@tierkit/core`/`@tierkit/agent` where it already lives). Every tool call passes through the relevant subset.

| Gate | Applies to | Source |
|---|---|---|
| Workspace boundary | all tools | new in mcp-server (uses `safePath` from `@tierkit/agent`) |
| Ignore globs | path-touching tools | `.tierkit/ignore` + `.gitignore` + bundled ignore list |
| Secret redaction | `read_file`, `codebase_search`, `list_files` output | existing engine in `@tierkit/core/security` |
| Approval gate | `apply_patch`, `run_command` | existing approval mechanism + new `/v1/mcp/patches/:id/{approve,reject}` |
| Command-gate classifier | `run_command` | existing classifier in `@tierkit/agent/tools/executeCommand.ts` |
| Diff preview | `apply_patch` (before approval) | new UI panel in GUI consumes `GET /v1/mcp/patches` |
| Activity logging | all tools | reuse `usageLog.ts` with new `type: "mcp-tool"` field |
| No telemetry / no cloud sync | global | enforced by absence of network egress in mcp-server package |

## 9. Claude Code integration

### Onboarding helper

A new card in the GUI's onboarding panel (`gui.ts`):

```
┌─ Connect Claude Code (MCP) ────────────────────────────┐
│ Let Claude Code, Claude Desktop, or Claude CLI use     │
│ Tierkit's gated tools for safe file editing and        │
│ command execution.                                      │
│                                                         │
│   [Show config snippet]   [Copy to clipboard]          │
│   [Open ~/.claude/settings.json]                       │
└─────────────────────────────────────────────────────────┘
```

Clicking "Show config snippet" calls `GET /v1/mcp/config` and renders:

```json
{
  "mcpServers": {
    "tierkit": {
      "command": "tierkit",
      "args": ["mcp", "serve", "--workspace", "/Users/.../project"]
    }
  }
}
```

The exact Claude Code config file path and merge semantics are out of scope for v0.15.0 — we surface the JSON and let the user paste it. Auto-merge into `~/.claude/settings.json` is a v0.15.1 candidate, gated on the user's explicit consent.

### Verification

After the user pastes the config and restarts Claude Code, they can verify via:

```
> /mcp
```

(Claude Code's MCP status command shows whether the `tierkit` server connected.)

A future enhancement: a `tierkit mcp ping` command that simulates the MCP handshake and verifies the server can be spawned successfully.

## 12. Acceptance criteria

The release is done when **all** of the following hold:

1. `pnpm -F @tierkit/mcp-server test` passes; coverage ≥ 90% lines.
2. `tierkit mcp serve --workspace <path>` starts, completes an MCP `initialize` exchange, and responds to `tools/list` with all 7 tools.
3. A real Claude Code session configured with the suggested `mcpServers.tierkit` block can:
   - call `tierkit.list_files` and receive the workspace contents
   - call `tierkit.read_file` on a file containing a fake API key and receive **redacted** content
   - call `tierkit.propose_patch` and receive a `patchId`
   - call `tierkit.apply_patch({ patchId })` and observe the file mutation
   - call `tierkit.run_command` for a safe command and observe execution
   - have a dangerous `tierkit.run_command` (e.g., `rm -rf /tmp`) refused
4. The Tierkit GUI shows a "Connect Claude Code (MCP)" card with the correct workspace path baked into the JSON snippet.
5. Pending patches show up at `GET /v1/mcp/patches`; approving via `/v1/mcp/patches/:id/approve` unblocks the corresponding `apply_patch` call.
6. `tierkit.config.json` `disabledProfileIds`, `runtime`, and other existing settings continue to work — MCP is additive.
7. `pnpm typecheck`, `pnpm lint`, and `pnpm test` are green across the monorepo.
8. CHANGELOG, README, and `docs/MCP_BRIDGE.md` published.

## 13. Open questions deferred to v0.15.1

- **Auto-merge config into `~/.claude/settings.json`** — needs explicit consent UI + idempotent JSON patch.
- **Per-session approval persistence** — should "approve once for this Claude Code session" be a thing, vs. per-call approval? Default: per-call. Revisit if users complain about friction.
- **Streaming long file reads** — MCP supports content streaming; v0.15.0 returns full content. v0.15.1 can chunk if files large.
- **`git_*` tools** — defer until usage data shows demand.
- **`delete_file`** — defer for the same reason.
- **Codex CLI / other clients** — once Codex supports MCP, the same server should work without changes. No code path needed in v0.15.0.
