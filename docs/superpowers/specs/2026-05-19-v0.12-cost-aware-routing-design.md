## §1. Identity & scope

**Theme:** Teach Tierkit the difference between **free**, **flat-rate (subscription)**, and **per-token** profiles, and let the user cap each per-token profile's monthly spend in **USD and/or input tokens** independently.

**One-line:** Cost-aware routing v2 adds the *payment model dimension* and *per-profile budget enforcement*. v0.13 will add the routing reorder that prefers flat-rate over per-token once subscription-CLI execution exists.

**Strategic logic:** the strongest cost lever for many users isn't *local vs cloud* but *subscription vs API key*. A Claude Max $100/mo user prefers Claude Code (already paid, ~zero marginal cost) over a per-token Anthropic API key every time. Tierkit needs to know this distinction to route intelligently. v0.12 adds the data dimension and budget enforcement; v0.13 plugs in subscription-CLI execution and the routing reorder.

**v0.12 user outcome:**

- Set `claudeSonnet` profile's monthly cap to `$20` OR `200k` input tokens, whichever is reached first.
- Router refuses calls past the cap with clean fallback to the next candidate.
- Sidebar shows per-profile budget bar with text status: `Warning (82% USD)`.
- One source of truth: `tierkit.config.json` `budget.perProfile`.

**Out of scope (deferred):** subscription CLI subprocess provider (v0.13), CLI install/auth detection panel (v0.13), routing reorder to prefer flat-rate (v0.13 — needs the execution path), local LLM rerank/compress (v0.14), Savings Intelligence with monthly cap projection (v0.15), shared per-API-key budgets (v0.13 candidate), output token caps (not planned; may add later if requested), daily/monthly call count caps (not planned; v0.12 focuses on input-token and USD caps first).

## §2. Data model changes

### `PaymentModel` enum on `ModelProfile`

```ts
// packages/core/src/model/ModelProfile.ts

export const PAYMENT_MODELS = ["free", "flat-rate", "per-token"] as const;
export type PaymentModel = (typeof PAYMENT_MODELS)[number];

/**
 * free:
 *   Zero marginal token cost from Tierkit's perspective.
 *   May still involve hardware, electricity, or rental cost (e.g., owned GPU,
 *   home server). "Free" here means Tierkit will not bill or budget-gate
 *   per-call — it does not mean the user pays nothing in total.
 *
 * flat-rate:
 *   Subscription or fixed-cost access. Examples: Claude Code Max / ChatGPT Pro
 *   on Codex CLI, monthly rented GPU, fixed internal budget. NOT necessarily
 *   unlimited — subscription products typically have usage limits that Tierkit
 *   may want to protect against (via input-token caps), even if there is no
 *   per-call USD cost.
 *
 * per-token:
 *   Metered API billing by input and/or output tokens. Examples: direct
 *   Anthropic / OpenAI / Google API keys.
 */

export const ModelProfileSchema = z.object({
  // ... existing fields unchanged ...
  paymentModel: z.enum(PAYMENT_MODELS).optional(),
}).strict();

/** Derive the effective paymentModel from a profile. Explicit value wins. */
export function effectivePaymentModel(p: ModelProfile): PaymentModel {
  if (p.paymentModel) return p.paymentModel;
  switch (p.kind) {
    case "local-device":   return "free";
    case "private-remote": return "free";       // self-hosted Ollama/vLLM is the common case
    case "public-cloud":   return "per-token";  // API-key profiles
    default: {
      const _exhaustive: never = p.kind;
      return _exhaustive;
    }
  }
}
```

**Why `private-remote` defaults to `"free"`:** the common case is self-hosted Ollama/vLLM/llama.cpp on owned or rented-flat-rate hardware. Rented per-token private endpoints are rare; they opt in via explicit `paymentModel: "per-token"`. Minimizes config friction for the common case.

### `PerProfileBudget` on `BudgetPolicy`

```ts
// packages/core/src/config/TierkitConfig.ts

export const PerProfileBudgetSchema = z.object({
  dailyUsdLimit:           z.number().nonnegative().optional(),
  monthlyUsdLimit:         z.number().nonnegative().optional(),
  /**
   * Input-token caps only. Tierkit's first optimization target is cloud input
   * context, so input is what we cap and report. USD budgets, when provider
   * pricing is available, already account for both input and output costs
   * post-call. Output-token caps may be added in a later version if needed.
   */
  dailyInputTokenLimit:    z.number().int().nonnegative().optional(),
  monthlyInputTokenLimit:  z.number().int().nonnegative().optional(),
}).strict();

export const BudgetPolicySchema = z.object({
  dailyUsdLimit:    z.number().nonnegative().optional(),  // existing global
  monthlyUsdLimit:  z.number().nonnegative().optional(),  // existing global
  /** Per-profile budgets (USD OR input tokens — whichever cap reached first). */
  perProfile:       z.record(z.string(), PerProfileBudgetSchema).optional(),
}).strict();
```

**Semantics (whichever-first):**

- A profile with `monthlyUsdLimit: 20` AND `monthlyInputTokenLimit: 200_000` is blocked when **either** is reached.
- A profile with only `monthlyUsdLimit: 20` is blocked only on USD; tokens unbounded.
- A profile with no `perProfile` entry → only global budget applies (v0.11.x behavior).

**Boundary:** `>` comparison. **At-limit allowed, over-limit blocked.**

## §3. Routing & budget gate behavior

### Gate position

```
profile pick → buildContext → redact → 【checkPerProfileBudget】 → provider.stream → usageLog
```

The gate sits **after `redact`** and **before `provider.stream`**. This positions the check against the final `ChatRequest` that would actually be sent — accurate input-token estimate, no surprises from upstream transformations.

### Per-`paymentModel` enforcement rules

| paymentModel | USD cap enforced? | Input token cap enforced? | On block |
|---|---|---|---|
| **per-token** | ✅ — both daily and monthly if set | ✅ | Skip candidate; escalate via existing fallback-chain mechanism |
| **flat-rate** | ❌ — surfaced in GUI as `Fixed monthly cost: $X — metadata only` | ✅ — subscription/quota protection | Same fallback |
| **free** | ❌ — `tierkit doctor` warns if set | ✅ — local-resource protection | Same fallback |

USD limits set on flat-rate or free profiles are **not enforced**. They render as metadata in the GUI and trigger a doctor warning suggesting the user move to `monthlyInputTokenLimit` instead.

### `checkPerProfileBudget` algorithm

```ts
function checkPerProfileBudget(
  profile: ModelProfile,
  request: ChatRequest,            // post-redact, final
  usageLog: UsageEntry[],
  budgets: PerProfileBudget,
): "ok" | { blocked: true; reason: string } {
  const pm = effectivePaymentModel(profile);
  const monthUsage = aggregateMonth(usageLog, profile.id);  // {inputTokens, costUsd, ...}
  const dayUsage   = aggregateDay(usageLog, profile.id);

  const estInputTokens = estimateRequestTokens(request);

  // 1. Input-token caps (all paymentModels, when set)
  if (budgets.dailyInputTokenLimit !== undefined &&
      dayUsage.inputTokens + estInputTokens > budgets.dailyInputTokenLimit) {
    return { blocked: true, reason: `daily input token cap reached (${budgets.dailyInputTokenLimit})` };
  }
  if (budgets.monthlyInputTokenLimit !== undefined &&
      monthUsage.inputTokens + estInputTokens > budgets.monthlyInputTokenLimit) {
    return { blocked: true, reason: `monthly input token cap reached (${budgets.monthlyInputTokenLimit})` };
  }

  // 2. USD caps — per-token only
  if (pm === "per-token" && profile.cost) {
    const estUsd = (estInputTokens / 1_000_000) * profile.cost.inputUsdPer1M;
    if (budgets.dailyUsdLimit !== undefined &&
        dayUsage.costUsd + estUsd > budgets.dailyUsdLimit) {
      return { blocked: true, reason: `daily USD cap reached ($${budgets.dailyUsdLimit.toFixed(2)})` };
    }
    if (budgets.monthlyUsdLimit !== undefined &&
        monthUsage.costUsd + estUsd > budgets.monthlyUsdLimit) {
      return { blocked: true, reason: `monthly USD cap reached ($${budgets.monthlyUsdLimit.toFixed(2)})` };
    }
  }

  return "ok";
}
```

**USD-block semantics:**
- Pre-call estimate uses **input tokens only** (output unknown until response).
- Post-call records both input + output actual cost into the usage log.
- Subsequent calls block on the **accumulated actual** cost. A single call can therefore exceed cap by its own output cost; future calls catch up.

### Same API key across multiple profiles

`claudeSonnet` and `claudeHaiku` both using `ANTHROPIC_API_KEY` — v0.12 tracks budgets **per profile**, not per API key. Users wanting account-level coordination must set per-profile caps that sum appropriately. Per-API-key shared budgets are a v0.13 candidate.

### Fallback chain integration

Budget-block reuses the existing `notGoodAt` skip mechanism in `runRoute`. Each skipped profile contributes a reason to a running list:

```ts
type RunRouteFail =
  | { ok: false;
      code: "budget-exceeded";
      message: string;
      details?: Array<{ profileId: string; reason: string }>;
    }
  | { ok: false; code: "..."; message: string };
```

If all candidates in the chain are budget-blocked:

```ts
{
  ok: false,
  code: "budget-exceeded",
  message: "All candidate profiles were skipped by budget policy.",
  details: [
    { profileId: "claudeSonnet", reason: "monthly USD cap reached ($20.00)" },
    { profileId: "claudeHaiku",  reason: "monthly input token cap reached (200,000)" },
    { profileId: "gpt4o",        reason: "daily USD cap reached ($5.00)" },
  ],
}
```

### Status text computation

```ts
const usdRatio    = monthlyUsdLimit ? monthlyUsdUsed / monthlyUsdLimit : 0;
const tokenRatio  = monthlyInputTokenLimit ? monthlyInputUsed / monthlyInputTokenLimit : 0;
const ratio = Math.max(usdRatio, tokenRatio);
const reason = usdRatio >= tokenRatio ? "USD" : "input";

const status =
  ratio >= 1.0  ? `Blocked (${reason})`             :
  ratio >= 0.95 ? `Near limit (${Math.floor(ratio*100)}% ${reason})` :
  ratio >= 0.80 ? `Warning (${Math.floor(ratio*100)}% ${reason})`    :
  ratio > 0     ? `OK (${Math.floor(ratio*100)}% ${reason})`         :
  "—";
```

Color is **additive** to the text — never the sole signal (accessibility):

| Status | Bar color | Text label |
|---|---|---|
| OK (<80%) | green | `OK (X% USD)` or `OK (X% input)` |
| Warning (80–94%) | amber | `Warning (X% USD)` |
| Near limit (95–99%) | red | `Near limit (X% input)` |
| Blocked (≥100%) | red, full | `Blocked (monthly USD cap)` |

### Aggregate row

```
─── 이번 달 per-token 지출 ────────────
▓▓▓░░░░░░░░  $5.30 / $30.00  (17.6%)
```

Shown only when at least one per-token profile has a USD cap set. Aggregate = `sum(monthlyUsdLimit over per-token-profiles-with-cap)` vs `sum(this-month-actual over same)`. Free + flat-rate excluded from this sum.

## §5. CLI: `tierkit usage --by-profile` / `tierkit doctor` extensions

### `tierkit usage --by-profile` (new flag)

Without the flag, output is **unchanged** from v0.11.x (aggregate only — backward compatible).

With the flag:

```
$ tierkit usage --by-profile

Today (2026-05-19)
  Calls:        14
  Input tokens: 51,681
  Cost:         $0.32

This month (2026-05)
  Calls:        128
  Input tokens: 412,000
  Cost:         $5.93

Per-profile (this month):
  Profile         pm          Monthly USD cap   Monthly input cap   Status
  claudeSonnet    per-token   $20/mo            200k/mo             OK (27% USD)
  claudeHaiku     per-token   —                 —                   —
  gpt4o           per-token   $10/mo            —                   OK (5% USD)
  localCoder      free        —                 —                   —
```

Column rules:
- `pm`: paymentModel — `free / flat-rate / per-token`
- `Monthly USD cap`: `$X/mo` or `—` (no cap)
- `Monthly input cap`: `Xk/mo` or `—`
- `Status`: same scheme as GUI (`OK (% reason) / Warning / Near limit / Blocked / —`)

`tierkit usage --json` outputs the raw `/v1/usage` body verbatim (additive `profiles` field included — clients may consume).

### `tierkit doctor` — 3 new checks

```
$ tierkit doctor

✓ Workspace config found at /Users/.../tierkit.config.json
✓ User config found at ~/.tierkit/config.json
✓ Ripgrep installed (v15.1.0)
✓ Daemon reachable at 127.0.0.1:4101 (v0.12.0)

⚠ profile 'localCoder' has 'monthlyUsdLimit: 5' set, but paymentModel='free'
    USD caps are NOT enforced for free profiles. Tierkit will not surface
    this profile's USD spend in budget gating.
    Fix: remove the misleading limit, or use 'monthlyInputTokenLimit' instead.

⚠ profile 'claudeSonnet' is at 82% of monthly USD cap ($16.40 / $20.00)
    Estimated based on this month's daily average so far: cap reached in ~5 days.
    Consider raising the cap or pausing per-token calls for this profile.

🛑 profile 'gpt4o' is blocked by monthly USD cap ($10.00 reached).
    Routing to this profile will be skipped until next reset (monthly: 2026-06-01)
    or until cap raised.

✓ All other profiles within budget thresholds.
```

The 3 new doctor checks:

1. **`flat-rate-or-free-with-usd-limit`** — `paymentModel ∈ {free, flat-rate}` and `monthlyUsdLimit` or `dailyUsdLimit` is set. Severity: warning.

2. **`per-profile-budget-near-threshold`** — `paymentModel === "per-token"` and `max(usdRatio, tokenRatio) ∈ [0.80, 1.0)`. Severity: warning. The "cap reached in ~N days" line appears **only** when all of the following hold (else line is omitted):
   - `paymentModel === "per-token"`
   - some monthly cap set
   - current ratio ≥ 50%
   - day-of-month ≥ 3
   - profile not yet blocked
   - daily average input tokens > 0

   The line always carries the footnote `Estimated based on this month's daily average so far.` to make the assumption explicit. Computation: `(usedSoFar / daysIntoMonth * 30) - usedSoFar` divided by daily avg gives days until cap reached. Simple linear extrapolation.

3. **`per-profile-budget-blocked`** — `max(usdRatio, tokenRatio) ≥ 1.0`. Severity: blocker (red). Message: `"Routing to this profile will be skipped until next reset (daily: tomorrow / monthly: YYYY-MM-DD) or until cap raised."`

### `tierkit doctor` exit code policy

| Condition | Exit code |
|---|---|
| budget warnings (≥80%) | 0 |
| budget blocked (≥100%) | **0** (policy state, not a system failure) |
| config parse error | 1 |
| daemon unreachable | 1 |
| schema validation error | 1 |
| other existing fatal checks | 1 |

CI users who want budget block to fail their pipeline can wait for v0.13's `--strict-budget` (or `--fail-on-blocked-budget`) flag.

### `tierkit route run` `budget-exceeded` rendering

When `RunRouteFail.code === "budget-exceeded"` AND `details` is present:

```
$ tierkit route run "review this auth diff"
```

### `/v1/usage` response shape

Top-level `profiles` field is **optional** (additive). When present, each `profiles[id]` entry **always contains both `today` and `month`** with zero defaults for absent counters. Format:

```jsonc
{
  "total": { "calls": 128, "inputTokens": 412000, "costUsd": 5.93 },
  "today": { "calls": 14, "inputTokens": 51681, "costUsd": 0.32 },
  "profiles": {
    "claudeSonnet": {
      "today": { "calls": 1, "inputTokens": 1200, "outputTokens": 300, "costUsd": 0.12 },
      "month": { "calls": 8, "inputTokens": 18200, "outputTokens": 2100, "costUsd": 5.30 }
    },
    "localCoder": {
      "today": { "calls": 14, "inputTokens": 51681, "outputTokens": 800, "costUsd": 0 },
      "month": { "calls": 115, "inputTokens": 386700, "outputTokens": 5200, "costUsd": 0 }
    }
  }
}
```

If a profile has no calls this month, it still appears with all-zero `today` and `month`. Clients can rely on the consistent shape; old clients ignore the entire `profiles` field. Adding `profiles` is the only `/v1/usage` change — no query parameter dispatch, no separate endpoint.

## §6. Migration & backward compatibility

**No migration required.** All schema changes are purely additive optional fields:

| Field | Older behavior | New behavior |
|---|---|---|
| `ModelProfile.paymentModel` (new) | n/a | undefined → derived from `kind`; explicit value wins |

## Appendix A — Worked example: "I want my cloud bill capped at $30/mo"

```jsonc
{
  "version": "0.1",
  "modelProfiles": {
    "localCoder":    { "kind": "local-device",   "provider": "ollama",    "model": "qwen2.5-coder:7b" },
    "localFast":     { "kind": "local-device",   "provider": "ollama",    "model": "llama3.2:3b" },
    "claudeSonnet":  { "kind": "public-cloud",   "provider": "anthropic", "model": "claude-sonnet-4-6",       "apiKeyEnv": "ANTHROPIC_API_KEY" },
    "claudeHaiku":   { "kind": "public-cloud",   "provider": "anthropic", "model": "claude-haiku-4-5",        "apiKeyEnv": "ANTHROPIC_API_KEY" },
    "gpt4o":         { "kind": "public-cloud",   "provider": "openai",    "model": "gpt-4o",                  "apiKeyEnv": "OPENAI_API_KEY" }
  },
  "budget": {
    "monthlyUsdLimit": 30,           // hard ceiling — global
    "perProfile": {
      "claudeSonnet": { "monthlyUsdLimit": 20, "monthlyInputTokenLimit": 200000 },
      "claudeHaiku":  { "monthlyUsdLimit": 5 },
      "gpt4o":        { "monthlyUsdLimit": 5 }
    }
  }
}
```

Expected behavior:
- claudeSonnet calls allowed until $20 OR 200k input tokens (whichever first).
- claudeHaiku capped at $5.
- gpt4o capped at $5.
- Total cloud spend capped at $30 (global cap is the final backstop; per-profile caps sum to $30 ≤ global).
- Once any profile is blocked, fallback chain continues to local. Local-routable tasks keep working.
