# v0.16 — Tool Result Envelope + Windows Unlock — Design Spec

## TL;DR

v0.16 ships three tracks bundled together:

- **Track A (Windows unlock)** — two surgical bug fixes that prevent Windows users from getting through Tierkit at all today: the MCP card's `Failed to fetch`, and the subscription-CLI / health-probe spawn missing `shell: true`.
- **Track B (Tool Result Envelope)** — protocol redesign for long-output tools. Replaces ad-hoc text payloads with a structured JSON envelope carrying `truncated`/`range`/`size`/`next.cursor`/`next.suggestedCall`/`warnings`. The model gets a deterministic continuation path instead of re-reading the same file with no signal.
- **Track C (Timeout policy)** — make `transport.timeoutMs` per-profile overridable and bump the Claude Code default to 300s to absorb Windows subprocess latency. Documentation-and-config track, no protocol change.

Tracks A and C are mechanical. Track B is the architectural centerpiece and the source of most of this spec's text.

## Why this exists (what was observed)

Running Tierkit on Windows with `claudeCode` as the routed model on the prompt _"프로젝트 전반을 살펴보고 리뷰해줘"_ produced:

1. **`Error: TypeError: Failed to fetch`** in the sidebar's "Connect Claude Code (MCP)" card when the user clicks _Show config snippet_.
2. **`라우팅 흐름: ? ⚠ no viable candidate`** in the Setup card's quick-test trace.
3. **A 4-turn / 5173-output-token agent loop** that read the same file two and three times in a row, called `search_files` with the wildcard pattern `.*` as a (failed) workaround, hit a mid-flow `[cli-timeout]`, and eventually produced a project summary. Useful output was buried under repeated truncated re-reads.

Each symptom maps to a different layer of the stack. v0.16 fixes all three layers in one release because shipping any subset leaves Windows users still broken.

## Track A — Windows unlock (bug fixes, no design choice)

### A.1 — `gui.ts` MCP snippet button uses raw `fetch()` instead of `jget()`

[gui.ts:4724](packages/core/src/runtime/ui/gui.ts#L4724) calls `await fetch('/v1/mcp/config')` directly. In a VS Code webview the relative URL resolves against the webview's own origin (`vscode-webview://…`), not the local daemon's loopback port. `TypeError: Failed to fetch` is the result.

Every other GUI call in the same file goes through `jget(p)` / `jpost(p, body)`, which routes through `transport.request(...)` — in VS Code mode the transport does `postMessage` so the extension host proxies the request over real HTTP to the daemon.

**Fix:** replace `await fetch('/v1/mcp/config')` with `await jget('/v1/mcp/config')`. The result of `jget` is already the parsed JSON body, so the surrounding code simplifies to a single `await` and direct use. The MCP patches panel in the same code block (`renderMcpPatches`) is already correct; this is the only outlier.

**Test:** GUI unit test (or browser-only smoke) that the snippet button populates the output pre-element when the transport returns a successful response, and renders an error message when it does not.

### A.2 — subscription-CLI / health-probe `spawn` missing `shell: true` + env propagation

Three call sites use `child_process.spawn(command, args, { stdio: [...] })` without `shell: true`:

- [packages/core/src/model/providers/subscriptionCli.ts:42](packages/core/src/model/providers/subscriptionCli.ts#L42) — `chat()` path
- [packages/core/src/model/providers/subscriptionCli.ts:255](packages/core/src/model/providers/subscriptionCli.ts#L255) — `stream()` path
- [packages/core/src/model/profileViability.ts:61](packages/core/src/model/profileViability.ts#L61) — health probe path

On Windows, npm-installed CLIs (`claude`, `codex`) are typically `claude.cmd` shims. Without `shell: true`, Node's `spawn` does not consult `PATHEXT` and refuses to launch the `.cmd`, returning `ENOENT`. The Setup card's "✅ claude CLI" check uses a different path (a simple existence probe) and succeeds — masking the real failure inside the viability probe and the actual `chat()`/`stream()` call. The user sees "no viable candidate" with no explanation.

A related issue: both methods declare an `env: Record<string, string | undefined>` parameter and never pass it to `spawn`. The `chat()` parameter is even prefixed with `_env`, signaling deliberate non-use. This is fine on macOS/Linux because the child inherits `process.env`, but on Windows it means we cannot inject `PATHEXT` overrides or provide test fixtures without spawning in `process.env` mode.

**Fix:**

Introduce a shared `runChild(command, args, opts)` helper in a new file `packages/core/src/model/providers/runChild.ts` and route all three spawn sites through it. The helper:

```ts
import { spawn, type SpawnOptions } from "node:child_process";

interface RunChildOptions extends Omit<SpawnOptions, "shell" | "env"> {
  callerEnv?: Record<string, string | undefined>;
}

export function runChild(command: string, args: string[], opts: RunChildOptions) {
  return spawn(command, args, {
    ...opts,
    // Windows-only: route through cmd.exe so PATHEXT resolves .cmd/.bat shims
    // (npm-installed CLIs like `claude` ship as .cmd on Windows). macOS/Linux
    // keep the direct spawn behavior — adding /bin/sh -c there would change
    // quoting/escaping for command values we don't fully control.
    shell: process.platform === "win32",
    env: mergeEnv(process.env, opts.callerEnv),
  });
}

function mergeEnv(
  base: NodeJS.ProcessEnv,
  extra?: Record<string, string | undefined>,
): NodeJS.ProcessEnv {
  // Node accepts ProcessEnv, but a stray `undefined` value from a caller can
  // surface as the literal string "undefined" in the child. Strip them.
  const merged: Record<string, string> = {};
  for (const [k, v] of Object.entries(base)) {
    if (typeof v === "string") merged[k] = v;
  }
  if (extra) {
    for (const [k, v] of Object.entries(extra)) {
      if (typeof v === "string") merged[k] = v;
      else if (v === undefined) delete merged[k];
    }
  }
  return merged;
}
```

Then update the three call sites:

1. `subscriptionCli.ts:42` (chat path) — `spawn(...)` → `runChild(...)`.
2. `subscriptionCli.ts:255` (stream path) — same.
3. `profileViability.ts:61` (health probe) — same.

Rename `_env` → `env` in `SubscriptionCliProvider.chat()` and pass it through as `callerEnv`. `stream()` already names it `env`; it just needs to be forwarded.

**Why Windows-only `shell:true`, not always-on:**

- On Windows the `.cmd` shim resolution requires `cmd.exe`'s PATHEXT logic.
- On macOS/Linux, adding `/bin/sh -c` would change argument quoting/escaping for any `transport.command` that contains spaces or shell metacharacters. We do not fully control those values (user config), so preserving the v0.15 direct-spawn behavior is safer.
- `process.platform === "win32"` is a stable Node API and unit-testable by mocking `process.platform` in tests.

**Test:**

- Vitest on `mergeEnv()`: `undefined` values are stripped from both sources; `string` overrides win; an empty extra preserves base intact.
- Vitest on `runChild()` with `process.platform` mocked to `"win32"`: confirms `shell: true` is set on the spawn options. Mocked to `"linux"`: confirms `shell: false` (or absent).
- Subprocess integration test on host: `runChild("node", ["-e", "console.log(process.env.TIERKIT_TEST)"], { callerEnv: { TIERKIT_TEST: "ok" } })` prints `ok` on the actual platform the test runs on.

### A.3 — accept that this surfaces only on Windows

We will not add a "Windows CI runner" in v0.16. That is a v0.17 follow-up. v0.16 documents the manual smoke procedure in `docs/RELEASE_TESTING.md` (new): on a Windows machine, install the vsix, configure `claudeCode` profile, run the quick-test from the Setup card, confirm a winning candidate is shown.

## Track B — Tool Result Envelope (the architectural centerpiece)

### B.1 — Why a structured envelope, not stronger prompting

The observed loop —

```
read_file foo.ts → truncated (no continuation hint)
  → re-read foo.ts (same call, same result)
  → search_files pattern=".*" foo.ts (model's wildcard workaround)
  → still truncated
  → eventual partial answer + many wasted tokens
```

— is not a model intelligence problem. The model is making locally reasonable moves given the protocol it was given: the tool said "(1285 more bytes)" and nothing else. There is no way to continue, so the model retries.

Stronger prompting is a soft protocol — the model has to remember the rule on every turn, has to compute the next offset itself, and has to trust a hint with no machine-verifiable cursor. A structured envelope is a hard protocol — the tool tells the model the exact next call. Tierkit's value proposition is token economy. The envelope is the right fix.

### B.2 — Envelope schema (version `tool-result-envelope.v1`)

The shape is defined in TypeScript as the union of a success arm and a failure arm.

```ts
type ToolResultEnvelope<TData = unknown> =
  | ToolResultSuccess<TData>
  | ToolResultFailure;

interface ToolResultSuccess<TData> {
  ok: true;
  tool: string;                         // e.g. "read_file" — disambiguator for the model
  version: "tool-result-envelope.v1";   // schema version, frozen for v0.16
  data: TData;                          // tool-specific payload (see per-tool definitions)
  truncated: boolean;
  range?: {
    startLine?: number;
    endLine?: number;
    startByte?: number;
    endByte?: number;
  };
  size?: {
    bytesReturned?: number;
    totalBytes?: number;
    remainingBytes?: number;
    linesReturned?: number;
    totalLines?: number;
    remainingLines?: number;
  };
  next?: {
    cursor: string;                      // opaque to the model; base64url(JSON) inside
    suggestedCall: {
      tool: string;
      args: Record<string, unknown>;
    };
  };
  warnings?: string[];                  // soft signals, never trigger retry
}

interface ToolResultFailure {
  ok: false;
  tool: string;
  version: "tool-result-envelope.v1";
  error: {
    code: string;                       // see error-code list per tool
    message: string;
  };
  warnings?: string[];
}
```

### B.3 — Invariants (spec language, will land verbatim in the implementation plan)

1. **Every envelope MUST include `ok`, `tool`, `version`.**
2. **`version === "tool-result-envelope.v1"` for all v0.16 envelopes.** v0.17 may bump to `.v2` for additive changes; existing fields cannot be removed in `.v1`.
3. **If `truncated: true` AND deterministic continuation is possible, `next` MUST be present.** `next.cursor` is required; `next.suggestedCall` is required (the model copies it verbatim).
4. **If `truncated: true` AND deterministic continuation is NOT possible (e.g. `run_command`), `next` MUST be absent and `warnings` MUST explain the limitation.**
5. **`cursor` is opaque to the model.** The model never parses it. The daemon encodes / decodes it (base64url(JSON) in v0.16, with HMAC-signed variant a v0.17 option).
6. **When `cursor` is present in tool args, it is the source of truth.** All other args that overlap with cursor's encoded state (e.g. `path`, `startLine`, `maxLines`) are ignored. If the cursor is malformed or stale, the tool returns `ok: false, error.code: "cursor-invalid"` or `"stale-cursor"`.
7. **The envelope is serialized as JSON exactly once.** For Tierkit Agent the tool result `content` field is the JSON string. For MCP Bridge the MCP-level `{ content: [{ type: "text", text }] }` carries the JSON string as `text`. There is no double-encoding.

### B.4 — Per-tool definitions

#### read_file

**Args (v0.16):**

```ts
type ReadFileArgs = {
  path: string;
  startLine?: number;    // 1-indexed; default 1
  maxLines?: number;     // default 300; clamped to 1000
  cursor?: string;       // when present, source of truth — overrides above
};
```

**Defaults:** `maxLines` default 300, hard cap 1000. Callers passing `maxLines > 1000` get clamping plus a `warnings` entry: `"maxLines clamped to 1000"`.

**Data payload:**

```ts
type ReadFileData = {
  path: string;
  content: string;       // partial-but-valid if truncated
};
```

**Cursor encoding (decoded shape, never exposed to model):**

```ts
type ReadFileCursor = {
  tool: "read_file";
  path: string;
  nextStartLine: number;
  maxLines: number;
  fileHash: string;      // sha256 of full file at the time the cursor was issued — REQUIRED
  createdAt: string;     // ISO timestamp
};
```

Base64url-encoded JSON. v0.16 does not add HMAC. v0.17 may.

**Why `fileHash` is required, not optional:**

A best-effort cursor without integrity check produces the worst outcome: the model continues at `nextStartLine` of a file that has been edited mid-loop and silently reads the wrong content. Required `fileHash` lets the tool detect file change and return `stale-cursor`, signaling the model to restart the read.

For very large files where computing the hash on every issue + verify cycle is costly, v0.16 still computes it. v0.16.1 may add an opt-in `--unsafe-cursor` for files above a size threshold; for v0.16 correctness > speed.

**Error codes:** `not-found`, `not-a-file`, `path-escape`, `sensitive-file-blocked`, `read-error`, `cursor-invalid`, `stale-cursor`.

**Stale-cursor logic:** on every cursor-bearing call, recompute the file's `sha256` and compare to `cursor.fileHash`. If different, return `stale-cursor`. The model should retry without cursor (start fresh) or with a different starting point.

#### list_files

**Args:**

```ts
type ListFilesArgs = {
  path?: string;          // default "."
  recursive?: boolean;    // default false
  maxEntries?: number;    // default 200; clamped to 1000
  cursor?: string;
};
```

**Data payload:**

```ts
type ListFilesData = {
  path: string;
  entries: ListEntry[];
};

type ListEntry = {
  name: string;
  relPath: string;
  kind: "file" | "dir";
};
```

**Cursor:** `{ tool: "list_files", path, recursive, nextIndex, maxEntries, createdAt }` (no fileHash needed; directory listing changes are tolerated — caller gets fresh listing if it changed since cursor issued, and any duplicate entries are deduped by `relPath` client-side if needed).

**Error codes:** `not-found`, `not-a-directory`, `path-escape`, `read-error`, `cursor-invalid`.

#### search_files / codebase_search

**Args:**

```ts
type SearchFilesArgs = {
  pattern: string;
  path?: string;          // search root, default "."
  maxMatches?: number;    // default 50; clamped to 200
  contextLines?: number;  // default 2
  cursor?: string;
};
```

**Data payload:**

```ts
type SearchFilesData = {
  pattern: string;
  path: string;
  matches: SearchMatch[];
};

type SearchMatch = {
  path: string;
  line: number;
  snippet: string;       // redacted via redactOutput
  before?: string[];     // up to contextLines lines
  after?: string[];
};
```

**Cursor:** `{ tool, pattern, path, nextMatchIndex, maxMatches, createdAt }`.

**Search cursors are best-effort pagination cursors, not stable snapshots.** If files in the search root change between calls, the second call's `nextMatchIndex` may land on a different match than the first call would have produced. The model treats this as acceptable; v0.16 does not add a workspace snapshot hash to the cursor. A stable-snapshot cursor (storing `resultHash` or `workspaceSnapshotHash`) is a v0.17 candidate if drift becomes a real problem in practice.

**Error codes:** `invalid-query`, `pattern-too-broad` (warning, not error — `.*` triggers a `warnings` entry, not refusal), `path-escape`, `cursor-invalid`.

**Note on pattern=`.*`:** we observed the model trying this as a truncation workaround. v0.16 still allows it (refusing would be over-restriction), but adds a `warnings` entry: `"pattern matches every line; prefer read_file with startLine cursor for sequential file reads"`. This signals to the model that there's a better tool for the job.

#### execute_command / run_command

**Args (v0.16):** unchanged from v0.15.

```ts
type RunCommandArgs = {
  command: string;
  workspaceRoot: string;
  timeoutMs?: number;
  maxStdoutBytes?: number;   // default 64KB; ceiling = sandbox cap (1MB)
  maxStderrBytes?: number;   // default 32KB; ceiling = sandbox cap (256KB)
};
```

**Data payload:**

```ts
type RunCommandData = {
  exitCode: number;
  stdout: string;            // redacted via redactOutput
  stderr: string;            // redacted via redactOutput
  durationMs: number;
};
```

**Size fields:** because `run_command` has two truncation surfaces (stdout, stderr) rather than one, the envelope's `size` field uses stream-prefixed names:

```ts
size: {
  stdoutBytesReturned: number;
  stderrBytesReturned: number;
  stdoutTruncated: boolean;     // true if stdout hit maxStdoutBytes
  stderrTruncated: boolean;     // true if stderr hit maxStderrBytes
}
```

The envelope's top-level `truncated` flag is `stdoutTruncated || stderrTruncated`.

**Continuation policy:** if `truncated: true`, **`next` is absent**. Re-running a command is not deterministic continuation (commands aren't idempotent). Instead, `warnings` carries a single fixed message regardless of which stream was truncated:

> `"command output was truncated. Re-run with narrower scope or redirect output to a file and use read_file with a cursor."`

We deliberately do NOT include the exact byte count in the warning. The byte counts are in `size`; the warning is for the model's action loop.

A future `read_command_output` tool that reads from `.tierkit/runtime/command-outputs/<id>.log` is **deferred to v0.16.1+** and explicitly out of scope here.

**Error codes:** `command-blocked`, `approval-required`, `command-timeout`, `spawn-failed` (existing — unchanged from v0.15).

### B.5 — What is NOT changed

The following tools keep their v0.15 shape because their results are small and uniquely shaped:

- `propose_patch` — returns `{ patchId, diff, files, risk, requiresApproval }`. Internally bounded.
- `apply_patch` — returns `{ applied, files, durationMs }` or an error envelope.
- `get_policy_status` — returns a fixed-shape snapshot.
- `task_complete` (Tierkit Agent control signal) — single `summary` field.
- `ask_followup_question` (Tierkit Agent control signal) — single `question` field.

The toolShim layer that converts Roo/Cline/Continue's OpenAI-format `tools` array into XML system-prompt instructions for local models is **untouched**. v0.16's envelope is an internal-to-Tierkit protocol for tool RESULTS, not inbound tool DEFINITIONS.

### B.6 — System prompt updates (secondary, but worth doing)

The Tierkit Agent's system prompt currently emits XML tool tags as the canonical call format and shows one example. v0.16 adds a short paragraph after the format example:

> Tool results return a JSON envelope. When `truncated: true` and `next.suggestedCall` is present, copy that call verbatim instead of re-issuing the original. If `warnings[]` is present, read it before deciding next action — a warning may indicate that a different tool is more efficient.

This is the **soft protocol** layer. The hard protocol is the envelope's machine-readable structure. Per the brainstorming decision: prompt is secondary; envelope is the primary protocol.

### B.7 — Telemetry / activity log

The MCP activity log entry shape (introduced in v0.15.0) gains optional fields:

```jsonc
{
  // existing fields:
  "ts": "...", "type": "mcp-tool", "tool": "...", "workspaceRoot": "...",
  "ok": true, "code": null, "durationMs": 12, "redactionHits": 1,
  "inputSummary": { "path": "src/foo.ts" },
  "outputSummary": { "bytes": 1287, "truncated": false },

  // new in v0.16:
  "envelope": {
    "truncated": true,
    "hasCursor": true,
    "remainingLines": 400
  }
}
```

This lets us measure, in production, how often the model successfully follows `next.suggestedCall` versus re-reading. v0.16.1 can derive a metric: `cursor_followed_rate = (calls_with_cursor / calls_after_truncation)`.

## Track C — Timeout policy

### C.1 — `transport.timeoutMs` is already per-profile, but the default is too aggressive for Windows

The `ModelProfile` Zod schema already allows per-profile `transport.timeoutMs`. The bundled `claudeCode` profile defaults to `180_000` ms (3 min). On Windows the user hit `[cli-timeout]` mid-flow at this default.

**Change:**

1. Bump bundled `claudeCode` profile's `timeoutMs` default to `300_000` (5 min).
2. Document the per-profile override in `docs/MODEL_PROFILES.md` (new section, "Tuning subscription CLI timeouts on slow systems").
3. The doctor command (`tierkit doctor`) gains a new check: if any subscription-CLI profile's recent invocations include `cli-timeout` results in `usage.jsonl`, emit a hint to raise `timeoutMs`.

### C.2 — Why this is its own track, not part of B

Timeout is "how long to wait." Truncation is "how to continue past a size cap." These are orthogonal. Bundling them muddies the v0.16 release narrative (the user explicitly said so during brainstorming). Track C ships in the same release but appears as its own CHANGELOG section.

## Acceptance criteria (release-ready)

1. **Track A.1** — Windows VS Code sidebar: clicking _Show config snippet_ in the MCP card populates the snippet pre-element instead of showing `TypeError: Failed to fetch`. Verified by manual test on Windows.
2. **Track A.2** — Windows quick-test trace: with `claudeCode` profile enabled and `claude.cmd` on PATH, `/v1/route/explain { task: "..." }` returns at least one viable candidate (claudeCode) instead of "no viable candidate". Verified by Vitest using a mocked `.cmd` shim on a synthetic PATH.
3. **Track B** — long-output tools return envelope shape:
   - Schema validation against `tool-result-envelope.v1` for `read_file`, `list_files`, `search_files`, `execute_command` in the Tierkit Agent.
   - Same schema validation for `tierkit.read_file`, `tierkit.list_files`, `tierkit.codebase_search`, `tierkit.run_command` in the MCP Bridge.
   - `read_file` with `cursor` continues correctly: a 1000-line file paginated with `maxLines: 300` returns 4 chunks (300+300+300+100), the 4th having `truncated: false`. Verified by Vitest.
   - `read_file` returns `stale-cursor` when `fileHash` no longer matches. Verified by Vitest.
   - **Behavioral regression tests** (deterministic, no live model):
     - Given a synthetic agent transcript where `read_file` returned `truncated: true` with a `next.suggestedCall` and the model's NEXT turn is replayed, assert the model's next call uses `cursor` (or matches the `suggestedCall` args). If the parser sees an identical-args `read_file` repeat, the test fails.
     - Given the same fixture extended to a third turn after a successful cursor read, assert NO repeat of the original `read_file(path, no-cursor)` call occurs.
     - Total tool-call count for the fixture's scenario ≤ baseline tool-call count captured from v0.15.0.
   - **Benchmark goal** (not a CI gate): on an equivalent live scenario, output tokens for the agent loop should drop to ≤ 60% of the captured v0.15.0 baseline. Manual measurement; recorded in the release notes, not gated by CI.
4. **Track C** — `claudeCode` profile has `timeoutMs: 300_000`. Doctor command surfaces a hint when recent timeouts exist.
5. **CHANGELOG** — three sections matching the three tracks. Track B clearly marked: `BREAKING for direct MCP/tool-result consumers — long-output tools now return a structured JSON envelope. Agents should inspect 'truncated' and 'next.suggestedCall'.`
6. **All existing tests still green** — `@tierkit/core`, `@tierkit/mcp-server`, `@tierkit/cli`, `@tierkit/agent`. The pre-existing `@tierkit/client/openaiCompat.test.ts:75` failure (HTTP 400 vs 404, present at the v0.15.0 baseline) remains a known unrelated issue.

## Out of scope / deferred

- `read_command_output` tool for paginating subprocess output — v0.16.1.
- Windows CI runner — v0.17.
- HMAC-signed cursors — v0.17 if cursor manipulation becomes a real concern.
- Refactoring `subscriptionCli.ts` to share a common `runChild()` helper between `probe`, `chat`, and `stream` — v0.16.1 cleanup.
- Migrating `propose_patch` / `apply_patch` to the envelope shape — not needed; their outputs are small and uniquely structured.
